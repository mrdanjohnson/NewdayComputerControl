# MacControl Project Status Report — 2026-10-07

Drawing on everything from the 2026-10-05→07 client rollout (first NDC client
install) plus the repo's own documentation. Direct assessment: the project is
**strong at its core** (spec-driven protocol, honest command ledger, excellent
docs culture) but has **structural weaknesses in testing, release engineering,
and fleet operations** that all surfaced the moment the first real client
install happened.

---

## 1. What the NDC rollout exposed (and we fixed)

This session's bugs weren't random — they share a root cause: **the project
was developed against one bench board and one bench Mac**, so everything
bench-specific was invisible:

| Bug | Root cause class |
|---|---|
| pip resolution failure on Python 3.9 | bench Mac runs Homebrew Python 3.14; clients run CLT 3.9 |
| Tk `abort()` crash-loop | Homebrew Python has no tkinter; CLT Python does |
| `Future attached to a different loop` | asyncio <3.10 binds eagerly; bench runs 3.14 |
| Serial provisioner never worked on real hardware | invented fixtures (`mc> ` prompt, echo assumption, `mckid_` ids) — never run against a real board until NDC |
| `key create` TWDT crash | only-ever-attempted on a factory-fresh device at NDC |

All fixed **except the last one** (see §2). The meta-lesson: *every new
client is a fuzzer.* Which leads to the biggest structural gap:

**There is no automated install-path testing.** The firmware has 156 native
unit tests and a real AT harness, but the agent/installer/provisioner had
*zero* tests — the only way anything got found this week was a human at a
client site reading errors. A cheap smoke test (sandboxed installer run +
daemon boot + `--selftest`) would have caught half of this.

## 2. Critical open issues (unanswered)

1. **Firmware task-watchdog crash during `key create`**
   (`firmware/docs/DEBUG-PROVISION-TWDT.md`). Root cause unidentified;
   repro'd once on a factory-fresh device right after WiFi association. The
   provisioner now retries around it, but *any* fresh install can hit it
   (serial or Web UI). **Blocker for confident multi-client rollout.** Next
   repro needs the full `Task watchdog got triggered` line (the starved task
   name was truncated in the paste).
2. **No bench board.** The only known S3 is at NDC. You cannot repro firmware
   issues, run the AT suite, or validate the next firmware build without
   either retrieving it or buying a second unit (~$25 — do this tomorrow;
   it's the cheapest insurance in the whole project).
3. **Committed OTA signing private key** (`firmware/keys/ota_dev.pem` is in
   git; its README admits it's public). Any device flashed with the
   compiled-in pubkey accepts OTA signed by *anyone who clones the repo*.
   Fine for dev; a real security hole the moment client devices matter.
   Production needs per-fleet key generation.

---

## 3. Under-developed

- **Release engineering is manual.** `dist/esp32-s3` is refreshed by hand and
  binaries are committed to git. Clients install from a raw `git pull`. No
  tags, no versions, no "this client got build X" traceability.
- **`maccontrol_agent` has no test suite** at all; the 156 tests all target
  `lib/maccontrol_core`.
- **The Tk agent UI is now dead code** (correctly skipped off-main-thread).
  Status visibility lives only in the endpoint Web UI — fine, but the docs
  should stop implying a Mac-side UI exists.
- **AT-11 bench-WS caveat** and other open items in HANDOFF's next-steps list
  (still pending from 10-03).

---

## 4. Poorly implemented (fixed this session, but worth naming the pattern)

- **Fixture-driven development of the serial path** — the provisioner was
  written against invented console output and went unexercised for weeks.
  House rule worth adopting: *any parser of device output gets its fixtures
  captured from real hardware, checked in with the capture log.*
- **Doc drift**: README/AGENTS described behavior (console echo, port-open
  reboots) as certainties; several were driver/cable-dependent. Docs now
  match reality, but the lesson is to label observed-vs-assumed in docs.

## 5. Missing "AAA" features, ranked

**Tier 1 — changes the business value:**

1. **Show-mode automation (the killer feature).** For the actual market
   (church/AV), the dream is one button — or a schedule — that does:
   *power-on at 06:00 → HID wake → unlock → launch ProTools (or presentation
   software) → verify*. Every piece exists (pmset failsafe, wake,
   device-stored unlock password, verified app launch, triggers). What's
   missing is the **sequencer**: an on-device "routines" concept that chains
   these with waits and verifies each step, plus a big "START SHOW" button in
   the Web UI. This is what turns a power-toy into a product.
2. **Fleet dashboard.** Now a multi-client operation. A lightweight status
   page (even a script polling each endpoint's `/api/v1/status` +
   agent/status) showing per-site: online/offline, mode, firmware version,
   agent session, last command result. All the data exists; nobody aggregates
   it.
3. **Config backup/clone.** LittleFS loss = total re-provision (lived in the
   Phase 6 migration; NDC macros were re-created by hand). Export/import
   macros+triggers as JSON, with templated "new client" bundles.

**Tier 2 — reliability that sells:**

4. **TWDT root-cause + watchdog hardening** (§2.1).
5. **Proactive alerting**: agent crash-loop, endpoint offline >N min, failed
   command records → webhook/email. Today a dead agent is silent until
   someone opens the Web UI (the NDC crash-loop lasted hours).
6. **Ethernet (W5500) option** — WiFi-only is the weakest link in RF-hostile
   sanctuaries; already scoped in PHASE6.md as deferred.
7. **Production OTA pipeline**: key management, signed dist bundles, staged
   updates.

**Tier 3 — polish:**

8. Operator runbook (non-technical): pairing, reboot-the-board ritual, "what
   the lights mean" — the installer prompts are good; the docs assume a
   developer.
9. Installer smoke tests + CI on a fresh macOS VM with CLT Python.
10. Web UI dashboard polish (awake/asleep badge is in HANDOFF's "optional"
    list — promote it).

   write the one-page "installing a new client" runbook from this session's

3. Build the fleet status script (Tier 1.2) — a day of work, immediate ops
   value.
4. Design the show-mode sequencer (Tier 1.1) — spec it before coding; it's
   the flagship.
5. Rotate the OTA key story before the next firmware release reaches
   clients.

**Bottom line:** the protocol and honesty model are genuinely excellent — the
ledger semantics and evidence-based command records are better than most
commercial AV control. What's missing is everything *around* the firmware:
tested installs, repeatable releases, fleet visibility, and the automation
layer that makes a church volunteer say "wow." The foundation is AAA; the
product wrapper is still prototype-grade.
